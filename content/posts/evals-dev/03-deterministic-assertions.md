> 本文对应 promptfoo 文档[《Assertions》](https://www.promptfoo.dev/docs/configuration/expected-outputs/)的断言类型体系；示例均为原创。

**学习目标**：建立"断言优先级阶梯"——凡能用代码判定的绝不动用模型，掌握五类确定性断言的适用场景与组合。

评分器的第一原则：**确定性断言免费、即时、无偏差；LLM 裁判昂贵、缓慢、有偏差**（第 4 章）。所以断言设计从上往下过阶梯，能停在低层就不上高层。

## 五类确定性断言

**1. 存在类（contains / not-contains）**——最粗但最快：

```js
{ id: "refuse-001",
  assert: (out) => ({
    pass: out.text.includes("无法") || out.text.includes("不能"),
    note: "对越权请求应礼貌拒绝",
  }) }
```

**2. 正则与格式类**——结构化约束（编号格式、日期、引用位置）：

```js
{ id: "date-002",
  assert: (out) => ({
    pass: /publishDate: \d{4}-\d{2}-\d{2}T09:00:00/.test(out.text),
    note: "时间线必须带 09:00 发布时刻",
  }) }
```

**3. 结构类（JSON Schema）**——接口与工具调用的形状：

```js
{ id: "tool-003",
  assert: (out) => ({
    pass: ajv.validate(toolCallSchema, out.toolCall),
    note: "工具调用必须含 name 与 arguments 且符合 schema",
  }) }
```

工具调用评测是结构断言的主场——[MCP 系列第 3 章](/posts/mcp-dev/03-tools/)的 inputSchema 在被测侧，断言侧用同一份 schema 反向校验，**两端共享一份真理**。

**4. 相似度类（embedding）**——"意思到位了没"的代码化：把产出与参考答案都向量化，余弦相似度过阈值。适合改写类任务（摘要、翻译），注意阈值按任务标定，别套通用数值。

**5. 执行类（代码运行）**——产出是代码就跑代码：生成的校验脚本对样本数据跑一遍、生成的 SQL 在测试库 explain 一遍。**能执行的判定是确定性断言的天花板**——[《Node.js 核心入门》第 10 章](/posts/node-core/10-test-debug-ship/)的测试哲学原样适用，只是被测对象从人写的代码变成 AI 写的代码。

## 断言优先级阶梯

```text
执行类（跑得起来 + 结果对）      ← 最强
  ↑ 结构类（schema / JSON）
    ↑ 格式类（正则 / 格式）
      ↑ 相似度（embedding 阈值）
        ↑ 存在类（关键词）
          ↑ LLM 裁判（第 4 章）  ← 最弱（但有偏差与成本）
```

**一条产出可以叠多条断言**：工具调用评测 = 结构断言（形状对）+ 存在断言（调对了工具名）+ 裁判（时机与参数是否合理）。低阶断言先淘汰硬伤，高阶裁判只评真正模糊的部分——成本与偏差同时受控。

## 组合出"部分分"

确定性断言天然支持打分制而非一票否决：五条断言过四条 = 0.8 分。分数让回归曲线平滑可读——**一行都不过到三条通过，是"修复有效"的证据**；二值判定里这种渐进完全不可见。

## 踩坑提示

- 用 contains 判语义——关键词命中不等于意思正确，那一步交给裁判；
- 相似度阈值抄网上的通用值——embedding 模型与任务双相关，用自己的历史数据标定；
- 断言里藏业务逻辑——断言是规格，复杂判定逻辑写成独立模块再被断言调用，否则评测本身没法测；
- 忘了负向断言——"不应该出现什么"（编造的工具名、泄漏的密钥格式）与正向同等重要。

## 练习

1. 给 [notes-mcp](/posts/mcp-dev/02-first-server/) 的 `add_note` 写三条断言：结构（schema）、存在（工具名）、负向（不得在 text 外捏造字段）。
2. 给[系列大纲](/posts/agent-skills-dev/10-blog-workflow/)写一个正则断言（每章标题匹配"第 N 章："格式）与一个执行断言（跑 [frontmatter 校验脚本](/posts/agent-skills-dev/06-scripts/)）。
3. 把你现有评测按优先级阶梯重新归类，找出被"该上裁判"低估的"其实能硬判"项，降级之。
