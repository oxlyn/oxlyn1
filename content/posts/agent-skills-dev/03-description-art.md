> 本文对应官方标准[《Specification》](https://agentskills.io/specification)的 description 章节与 [Claude Code 技能文档](https://code.claude.com/docs/en/skills)。

**学习目标**：把 description 从"随便写写"升级成"可靠的触发路由"——技能 80% 的日常问题出在这几十个字上。

技能的正文再精妙，**没被触发就等于不存在**。决定"用不用"的不是模型的心灵感应，而是每次会话都躺在上下文里的那段 description——模型读着全部技能的描述，为当前任务选工具。所以 description 的写作对象是**路由器**，不是人类读者。

## 黄金结构：做什么 + 何时用

一条合格的描述回答两个问题，各占一半篇幅：

```yaml
description: >-
  生成或校验博客文章的 frontmatter 元数据（title、description、publishDate、tags），
  输出符合站点 schema 的 YAML 头部。当用户要新建文章、修改文章元数据、
  frontmatter 校验报错，或询问文章字段规范时使用；纯正文写作或系列大纲规划不适用。
```

- **做什么**：动作 + 对象 + 产出（"生成或校验……输出……"）——动词开头，具体到字段级；
- **何时用**：正例触发场景 + **反例排除**（"……不适用"）——反例是防误触发的护栏，几乎没有成本却极其有效；
- **第三人称**：写"当用户……时使用"而非"我会帮你……"——它是元数据，不是对话。

## 触发词：替用户把"叫法"写全

用户不会念你的技能名。他们说的是"写篇周记""修一下这个报错"。把高频叫法**作为触发词写进描述**：

```yaml
description: >-
  …。触发词：新建文章、改 frontmatter、元数据报错、周记模板。
```

经验法则：列出你希望用户**三秒内想到**的三五个说法，每一个都该在描述里有对应的词。描述里没出现的同义词，路由器只能靠语义近邻猜——猜错率随距离上升。

## 字符预算：1536 与 when_to_use

描述区有硬上限：**description + when_to_use 合计在技能列表中截断于约 1536 字符**。用结构抗截断：

```yaml
description: >-
  生成或校验博客文章 frontmatter，输出符合站点 schema 的 YAML 头部。
  当用户新建文章或元数据报错时使用。
when_to_use: >-
  新建文章 / 修文章元数据 / frontmatter 报错 / 询问文章字段规范。
  不适用于正文写作或系列大纲（用 series-planner）。
```

- description 保最短完整版（被截断也自洽）；when_to_use 放触发词与反例清单；
- **指路兄弟技能**（"不适用于系列大纲，用 series-planner"）——技能库越大，互相导流越重要；
- 别为省字砍"何时用"——一条"只有做什么"的描述是误触发之源。

## 两个失败案例

**没触发**：description 写"帮助处理博客相关事务"——太宽泛，路由器无法判断当前任务是否命中；改成动作+场景后命中率立刻上来。

**误触发**：description 写"生成 Markdown 文件"——所有写文件任务都命中；加领域词（"博客文章"）与反例（"不适用于通用文档"）收窄。

调试方法见第 8 章；现在的纪律是：**改描述 = 改代码，改完用真实任务回归**。

## 多技能场景：描述即命名空间

技能超过十个后，描述还承担**区分度**职责。两条铁律：

- 每条描述包含**只有本技能才有的领域词**（frontmatter、series-planner 的"系列大纲"）；
- 相邻技能互相点名的排他关系（A 说"不含 B 的场景"，B 说"不含 A 的场景"）。

## 踩坑提示

- description 为空——自动触发直接失效，只能手动调用；
- 描述里写实现细节（"读取 ~/.claude 目录"）——浪费预算，路由器只关心做什么何时用；
- 一段话塞四个任务——拆成多个技能，一个描述只路由一件事（第 7 章）；
- 中英混杂的触发词遗漏——用户中文说"周记模板"，描述里只有英文 weekly report，等于没写。

## 练习

1. 给第 2 章的 `post-frontmatter` 补 when_to_use：三个触发词 + 两个反例，检查合计是否在预算内。
2. 构造一次误触发：把描述改宽泛，说一句无关任务观察误命中，再收窄修复。
3. 为同一个任务写三条不同 description，分别用三个自然语言说法测试命中率，体会措辞差异的影响。
