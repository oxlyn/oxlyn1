> 本文对应官方标准[《Specification》](https://agentskills.io/specification)与 [Claude Code 技能文档](https://code.claude.com/docs/en/skills)的安装层级章节。

**学习目标**：掌握技能库的组织原则——粒度、复用、层级与分发，让技能从"个人小抄"长成"团队资产"。

## 粒度：一技能一能力

技能数量上来之后，粒度决定生死。判断标准只有一条：**description 能不能用一句话说清"做什么+何时用"**。能，粒度就对；说不清，就太大；一句话说完却总在描述里写"另外还要……"，就太小。

```text
✅ post-frontmatter     —— 一件事：文章元数据
✅ series-planner       —— 一件事：系列大纲
❌ blog-assistant       —— 描述写了五件事，路由器无法命中
❌ fix-title-typos      —— 太碎，与 post-frontmatter 边界纠缠
```

太小的技能合并进宿主技能当一节；太大的拆成多个 + 导航页指路（第 5 章）。**粒度错了先拆分再调优**，描述技巧救不了错误的结构。

## 复用的三种形态

**1. 技能间引用**——A 的正文里可以写"完成 X 后，若涉及 Y，使用 series-planner 技能"。引用走名字（description 里的互指，第 3 章），不直接 include 文件——保持每个技能自包含，靠路由器串联。

**2. 模板资产**——多个技能共用同一模板时，模板放各自 `assets/` 还是共享？答案通常是**各自持有、内容一致**：技能是独立分发的最小单元（第 9 章），跨技能的文件级共享会把部署搞成依赖地狱。真有大家族的共享需求，用插件包（见下）。

**3. 组合编排**——复杂工作流 = 一个"总控技能"的指令里按顺序点名其他技能与脚本。注意编排逻辑写在总控的 SKILL.md 里，被编排的技能保持对编排无感知。

## 三级安装与优先级

| 层级 | 路径 | 谁维护 |
| --- | --- | --- |
| 企业级 | 托管配置目录下的 `.claude/skills/` | 组织策略 |
| 个人级 | `~/.claude/skills/` | 你自己 |
| 项目级 | `<repo>/.claude/skills/` | 团队，进 git |

优先级：**企业 > 个人 > 项目**。实践含义：个人级放"我的偏好"（个人写作习惯），项目级放"团队共识"（本站规范）——个人级同名技能会盖过项目级，调试"为什么团队规范没生效"时先查个人级有没有同名私货。

## 插件：技能的打包分发

技能可以被打进**插件包**（插件目录下的 `skills/`），安装后以 `插件名:技能名` 的命名空间调用。什么时候升级到插件：技能带上了自己的 MCP 服务器、斜杠命令、hooks 等一整套东西，或要面向外部用户分发。纯技能分享（下一节）不需要插件壳——**文件夹加 git 就是零成本的分发协议**。

## 团队技能库的 git 化

把项目级技能当源代码管理，四条约定：

- **进仓库、过 review**：description 与指令的改动同代码一样需要第二双眼睛（描述就是路由配置，改错一行全团队不触发）；
- **CHANGELOG 记行为变更**：指令变了 = 团队 AI 的行为变了，登记清楚；
- **回归任务清单**：仓库里放一个 `TESTING.md`，列三五个标准任务与预期产出，改完技能跑一遍（第 8 章展开）；
- **命名空间前缀**：`blog-`、`deploy-` 开头，多来源技能同库时不打架。

## 踩坑提示

- 个人级攒了一堆只对某个项目有意义的技能——挪进那个项目的 `.claude/skills/`，个人级只留跨项目通用的；
- 技能互相 include 对方文件——自包含被破坏，单独分享即失效；要共享走模板复制或插件；
- 团队技能没有 review 就合入——一条含糊的 description 会让整个团队在这个任务上"AI 突然变笨"；
- 用符号链接把技能链到网盘——加载器对真实路径敏感，同步盘的冲突副本会造成诡异的双技能。

## 练习

1. 审视你的技能清单，找出一个"太大"的拆成两个并互写排他描述，一个"太小"的合并进宿主。
2. 把 `post-frontmatter` 挪进某个仓库的项目级并提交 git，让同事（或另一个会话） review 描述。
3. 建一个 `TESTING.md`，为现有技能各写一条标准任务与预期产出，跑通全部回归。
