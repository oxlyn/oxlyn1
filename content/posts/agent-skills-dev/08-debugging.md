> 本文对应 [Claude Code 技能文档](https://code.claude.com/docs/en/skills)的调试指引与官方[技能仓库](https://github.com/anthropics/skills)的迭代实践。

**学习目标**：建立"技能不干活"的三层归因框架，学会用最小成本定位描述问题还是指令问题，把调试沉淀为回归清单。

技能是程序，程序就要调试。技能的故障只有三层，**先归因再动手**，别一上来就重写。

## 三层归因框架

```text
任务失败
├─ 第一层：没触发        → description 问题（第 3 章）
├─ 第二层：触发了但做错  → SKILL.md 指令问题（第 4 章）
└─ 第三层：做对了但贵    → 渐进披露设计问题（第 5 章）
```

每层的检查手段不同：

**第一层检查**：问 AI"当前有哪些技能可用"——列表里有没有它？有 → 读描述问自己：用户那句话里的关键词，描述里出现了吗？没有 → 补触发词。列表里根本没有 → 回到第 2 章的安装排查（路径、首行 frontmatter、YAML 语法；Claude Code 可用 `--debug` 看 frontmatter 解析错误）。另外检查开关字段：`disable-model-invocation: true` 的技能只能手动调用，自动触发永远不命中。

**第二层检查**：让它复述"你刚加载的技能正文说了什么"——复述不出来 → 加载了别的技能（描述撞车）；复述正确但产出错 → 指令有歧义，对照产出逐条找"它理解成了什么"，把误解写成防呆条文（第 4 章的自我完善循环）。

**第三层检查**：看这次会话的上下文消耗（DevTools 或会话详情）——激活一次吞掉大几千 token 且大多没用到 → 该拆文件了。

## 描述撞车：最常见的第二层故障

两个技能的描述都能匹配同一任务，路由器二选一，选错的那个"做了但做错"。修复三板斧：

1. 用 description 里的**排他反例**互相划界（"不适用于 X，用 yyy 技能"，第 3 章）；
2. 给每个描述一个**独家领域词**；
3. 还撞 → 说明两个技能该合并（第 7 章的粒度问题）。

## 回归任务清单：技能的测试套件

技能没有单测框架，但有更朴素的等价物——**标准任务清单**（第 7 章的 `TESTING.md`）：

```markdown
# post-frontmatter 回归清单
- [ ] "新建一篇 React 系列第 5 章" → 五字段齐全、日期顺延 09:00、tags 含"教程"
- [ ] "修一下这个文件的元数据" → 先读原 frontmatter，不丢 updatedDate
- [ ] "随便写点东西"（无关任务） → 不触发本技能
- [ ] 校验脚本对坏数据输出 FAIL 行且可据此修复
```

四条构成触发正例、边界输入、**触发反例**、脚本契约四个象限。纪律：**每次改 SKILL.md 都全量跑一遍**，如同改代码跑测试（与排队中的[测试系列](/posts/javascript-core/)同一哲学：改行为必回归）。

## 版本化的最小实践

技能没有内置版本机制，用 git 兜底：改动独立提交、提交信息写"改了什么行为"；重要技能在 frontmatter 的 `metadata` 里维护 `version` 与变更日期（它是自由 YAML map，正是为这类自管理元数据准备的）。回滚 = git revert——这是技能比"聊天里教一遍"优越的地方：**知识有了版本史**。

## 踩坑提示

- 凭感觉改描述不看归因——把指令问题当描述问题修，越修越乱；
- 回归只在出问题时跑——技能的"静默劣化"（改了 A 描述，B 的触发被抢走）只有全量回归能抓到；
- 用同一句话反复测触发——过拟合测试用语；清单里的触发句要与真实使用措辞同分布；
- 上下文审计只看总量不看构成——先确认多出来的 token 是激活成本还是 references 读多了，再动手优化。

## 练习

1. 故意把 `post-frontmatter` 的 description 改得与系列大纲技能重叠，用回归清单抓出撞车，再用排他反例修复。
2. 为你的每个技能建回归清单，凑齐四个象限，改动后全量跑一遍并记录结果。
3. 做一次上下文审计：激活某个技能完成一个任务，记录"发现/激活/执行"三阶段各消耗多少 token。
